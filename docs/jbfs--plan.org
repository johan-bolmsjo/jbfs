* Terminology
- Replica :: A networked host with storage that syncs the file system DAG and block layers.
- Block layer :: A sparse file "block layer" that may be backed by another layer. Layers
  are visited recursively to resolve file system block data on access. Layers are
  immutable except for when existing as a working copy during file updates (before
  commiting the update to the DAG).
- DAG :: Directed Acyclic Graph. Data structure likely to be used to track file updates
  (file name to content mapping).

** TODO CRDTs
- CRDT :: Conflict-free Replicated Data Type

Can CRDTs (e.g. Merkle-CRDT) be useful for implementing the FS? Most likely as
IPFS use "Merkle-CRDTs". Similar to Git DAG with automatic merge resolution?

- https://research.protocol.ai/publications/merkle-crdts-merkle-dags-meet-crdts/psaras2020.pdf
- https://josephg.com/blog/crdts-go-brrr/
- https://en.wikipedia.org/wiki/Conflict-free_replicated_data_type

I think using some kind of CRDT algorithm for file operations is a likely choice. The
loose plan right now is that file content will never be automatically merged but that file
operations such as renames, deletes and updates can be auto-merged by replicas. An
auto-merged file update would likely just choose what immutable data a file contains in
some deterministic fashion. Tools should be available to readily retrieve obsoleted file
content (similar to "git log" and "git show").

- Using a block layer approach to create immuatable layers of content updates? E.g. "B is

  - Drawbacks: Multiple layers, possibly unevenly distributed accross replicas represent a

- Clients manage file updates by using a writable block layer that backs a publised layer.
  Once committed, file content is immutable and published layers are read only (content
  addressed).

** TODO Replica reliability
The file system relies heavily cryptographic hash chains (similar to Git). The design
should take into consideration that replicas may experiance storage and RAM faults. A
replica may retrieve corrupted data from its file system or miss-calculate hash values due
to RAM bit flips.

Loose thought: Replicas validate each other and reports faults to some mediator. E.g.
"replica A received inconsistent data X from replica B". Such a fault could be due to
either A or B misbehaving.
